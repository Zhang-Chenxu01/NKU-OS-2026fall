## 三、实验整体逻辑分析

### 3.1 从初始化建立中断处理条件

Lab3 的主线是在内核已有启动环境上建立事件入口，使正在执行的代码能够因中断或异常暂时转入处理程序，并在处理完成后继续执行。内核可以打印启动信息，仅能说明启动路径已运行；持续的时钟服务还依赖入口地址、局部与全局中断使能、上下文保存恢复以及每次时钟事件的重新设置。

根据 [init.c](../code/kern/init/init.c)，当前 `kern_init()` 的相关调用顺序为：

```text
kern_init()
    ├── 清零 BSS，dtb_init()，cons_init()，打印启动与内核信息
    ├── idt_init()
    ├── pmm_init()
    ├── idt_init()          // 当前源码确实调用两次，报告保留此顺序
    ├── clock_init()
    ├── intr_enable()
    └── 无限循环，等待事件
```

`idt_init()` 在 [trap.c](../code/kern/trap/trap.c) 中将 `sscratch` 写为零，并将 `__alltraps` 的地址写入 `stvec`。尽管函数名和部分注释沿用 IDT 表述，当前 RISC-V 实现的实际操作是设置 Trap 向量寄存器。`trapentry.S` 将入口按四字节对齐，写入的入口地址低两位为零，对应直接入口方式：后续中断和异常进入同一个汇编入口，再由 C 代码分类。

[clock.c](../code/kern/driver/clock.c) 中的 `clock_init()` 设置 `sie` 的 `MIP_STIP` 位，调用 `clock_set_next_event()` 安排第一次时钟事件，并把 `ticks` 初始化为零。[intr.c](../code/kern/driver/intr.c) 中的 `intr_enable()` 设置 `sstatus.SIE`，开放 S 模式中断的全局使能。局部时钟使能与全局使能分别控制事件来源和接收时机；中断能否到达还依赖平台及固件已经提供的特权级路由条件。

### 3.2 Trap 进入与上下文保存

当事件进入 S 模式 Trap 处理时，硬件记录返回位置、事件原因以及相关状态，并根据 `stvec` 转入入口。`sepc`、`scause`、`sstatus` 等 CSR 提供处理依据，但通用寄存器和栈指针仍需由软件保存。C 函数调用会使用和改写寄存器，因此必须先构造可靠的 Trap frame，再调用 C 处理程序。

[trapentry.S](../code/kern/trap/trapentry.S) 已有 `SAVE_ALL` 框架：先将原 `sp` 暂存到 `sscratch`，再分配 `36 * REGBYTES` 的栈空间，按寄存器编号保存通用寄存器。原 `sp` 通过 `csrrw s0, sscratch, x0` 取回并写入编号 2 的槽位，同时清零 `sscratch`；`sstatus`、`sepc`、`sbadaddr`、`scause` 分别写入最后四个槽位。

当前 `defs.h` 将 `uintptr_t` 定义为 64 位无符号类型；RV64 下 `REGBYTES=8`，因此一个 Trap frame 占 288 字节。其布局与 [trap.h](../code/kern/trap/trap.h) 中的结构相对应：

| 槽位 | C 结构中的对应部分 | 保存内容 |
| --- | --- | --- |
| 0～31 | `struct pushregs gpr` | x0～x31；其中编号 2 对应 Trap 发生前的 `sp` |
| 32 | `tf->status` | `sstatus` |
| 33 | `tf->epc` | `sepc` |
| 34 | `tf->badvaddr` | 源码使用 `sbadaddr` 名称读取的异常相关地址信息 |
| 35 | `tf->cause` | `scause`，包含中断标志和原因码 |

汇编保存顺序也保护了被用作临时变量的 `s0`～`s4`：它们的原值在读取 CSR 前已经写入通用寄存器区。当前框架在原内核栈上建立现场，没有实现完整的用户栈与内核栈切换机制。

### 3.3 C 分发、事件处理与返回的设计链路

完整设计应当在保存现场后把 Trap frame 地址作为参数传给 `trap(struct trapframe *tf)`。已有 `trap()` 只调用 `trap_dispatch()`；分发函数利用 `(intptr_t)tf->cause < 0` 判断最高位，将中断交给 `interrupt_handler(tf)`，将同步异常交给 `exception_handler(tf)`。

处理完成后，控制流应回到汇编返回路径，按 Trap frame 恢复 CSR、通用寄存器和原栈指针，再执行 `sret`。`sret` 根据 `sepc` 和相关状态完成特权级与中断状态的返回，不能替代通用寄存器的恢复。本次中断函数不修改 `tf->epc` 或其他现场字段；异步中断处理结束后，应由统一返回路径恢复被打断的执行状态。

上述链路中，当前仍有明确缺口：`__alltraps` 在 `SAVE_ALL` 后尚未补入参数传递与对 `trap()` 的调用，`RESTORE_ALL` 仍为空，`exception_handler()` 也尚无定义。因此，这里描述的是各模块应形成的完整协作关系，当前内核尚未具备可验证的完整 Trap 往返能力。

### 4.1 Trap 入口与上下文恢复

#### 4.1.1 模块目标与接口约定

本部分对应 `trapentry.S` 中的 `lab3 function1 YOUR CODE` 标记。目标是在已有保存现场的基础上连接 C 处理程序，并在其返回后准确恢复 Trap 前的执行状态。入口与返回路径必须共同遵守 `struct trapframe` 的字段顺序和 C 调用约定。

`__alltraps` 是 `stvec` 指向的汇编入口；`SAVE_ALL` 在当前栈上建立 Trap frame；C 接口为 `void trap(struct trapframe *tf)`；`__trapret` 是当前汇编文件中的返回标签，调用 `RESTORE_ALL` 后执行 `sret`。这些符号和框架已经存在，但相关待实现区域尚未完成。

#### 4.1.2 上下文恢复需要维护的条件

保存现场之后，传给 C 函数的应是当前 Trap frame 的地址。C 调用返回时，`sp` 应重新指向调用前的同一个 Trap frame，才能按原偏移恢复现场。恢复过程还需要保留访问现场的基址，避免过早恢复原 `sp` 导致后续槽位读取错误。

`tf->epc` 和 `tf->status` 应反馈到返回所需的 CSR；通用寄存器则应恢复到各自原来的值。中断处理期间使用临时寄存器、参数寄存器或被调用者保存寄存器，都不应改变被打断代码观察到的状态。`trap_in_kernel()` 已通过保存的 `SSTATUS_SPP` 判断 Trap 前是否处于 S 模式，可用于理解特权级来源；更完整的跨用户态栈管理仍需另行设计和验证。

#### 4.2.2 scause 标志位与原因码

RV64 的 `scause` 最高位表示是否为中断，其余位表示原因码。分发函数保留完整的 `tf->cause` 用于区分中断与异常；本函数只在局部变量中移除最高位：

```c
uintptr_t cause = (tf->cause << 1) >> 1;
```

由于 `tf->cause` 为无符号类型，左移会移出原最高位，随后逻辑右移在最高位补零，其余 63 位原因信息保持不变。由此，带中断标志的 `IRQ_S_TIMER` 能与值为 5 的常量正确匹配，大于低位常见编号的未知原因也不会被错误截断。

该操作没有写回 `tf->cause`，所以后续现场打印和返回仍可观察原始原因。课程测试还会直接用不带中断标志的 `tf.cause = 15` 调用本函数；现有提取方式同样得到 15，并进入未知中断分支。

#### 4.2.3 已知中断分类与未知原因诊断

实现按照当前 `riscv.h` 已定义的常量分类，具体覆盖范围如下。

| 原因类型 | 常量及数值 | 当前处理 |
| --- | --- | --- |
| 软件中断 | `IRQ_U_SOFT=0`、`IRQ_S_SOFT=1`、`IRQ_H_SOFT=2`、`IRQ_M_SOFT=3` | 分别打印 User、Supervisor、Hypervisor、Machine 软件中断提示 |
| 时钟中断 | `IRQ_U_TIMER=4`、`IRQ_S_TIMER=5`、`IRQ_H_TIMER=6`、`IRQ_M_TIMER=7` | S 模式执行时钟服务；其余分支打印对应模式的时钟提示 |
| 外部中断 | `IRQ_U_EXT=8`、`IRQ_S_EXT=9`、`IRQ_H_EXT=10`、`IRQ_M_EXT=11` | 打印对应模式的外部中断提示 |
| 其他已定义类型 | `IRQ_COP=12`、`IRQ_HOST=13` | 分别打印 `Coprocessor interrupt`、`Host interrupt` |
| 未知原因 | 例如原因码 15 | 输出原因码并调用 `print_trapframe(tf)` |

S 模式软件中断的提示为 `Supervisor software interrupt`，与课程测试匹配。上述分类依据是项目头文件；当前只对 S 模式时钟实现了后续事件处理，其他分支的提示不代表已经完成相应中断源的确认、清除和设备服务。

未知分支保留原始现场，并以完整的无符号整数输出原因：

```c
cprintf("Unknown interrupt: cause %llu\n",
        (unsigned long long)cause);
print_trapframe(tf);
```

`%llu` 对应 `unsigned long long`。当前仓库中的 `uintptr_t` 实际经 `uint64_t` 定义为该类型；本次仍根据补充要求加入显式转换，使可变参数的类型约定直接可见。该修改没有改变原因码，也没有把前序完整构建的失败归因为格式化问题。

#### 4.2.4 时钟事件重新设置、计数与输出

S 模式时钟分支的处理顺序是先调用 `clock_set_next_event()`，再使 `ticks` 增加一次，最后检查是否需要输出。`clock.c` 中的实现为：

```c
void clock_set_next_event(void) {
    sbi_set_timer(get_cycles() + timebase);
}
```

RV64 路径的 `get_cycles()` 实际通过 `rdtime` 读取时间计数器；`timebase` 当前硬编码为 100000。传给 SBI 的是当前时间加间隔得到的下一次绝对时刻。`clock_init()` 只安排第一次事件，后续每次时钟处理都必须重新设置事件，才能形成持续的定时服务。只增加计数而遗漏该调用，无法保证后续时钟事件按预定节奏到来。

这里的 100000 是时间计数器单位，实际时间长度依赖平台的计数频率，本轮没有实测中断频率。`ticks` 记录进入并处理该分支的次数；`volatile` 使轮询代码能够重新读取该值，但不提供多核原子计数或完整的并发同步机制。

`print_ticks()` 固定输出 `100 ticks`。每当 `ticks` 是 `TICK_NUM=100` 的整数倍时调用它，表示又完成一组 100 次中断；打印文本本身不是当前累计值。检查累计值需要观察 `ticks`，或由测试程序单独输出该值。

#### 4.2.5 第三次统计输出后的关机策略

最终时钟分支如下，省略其余 switch 分支：

```c
case IRQ_S_TIMER:
    clock_set_next_event();
    ticks++;
    if (ticks % TICK_NUM == 0) {
        print_ticks();
        if (ticks / TICK_NUM >= SHUTDOWN_AFTER) {
            sbi_shutdown();
        }
    }
    break;
```

`SHUTDOWN_AFTER=3` 是本次补充指令明确指定的实现选择。初次源码检查未发现该宏，因此第一版没有自行假定阈值；后续才加入宏定义、`sbi.h` 和判断逻辑。

在 `ticks` 初始为零、每次时钟中断增加一次的前提下，恰逢输出时的 `ticks / TICK_NUM` 就是累计统计输出次数，无需另外维护计数变量。判断放在 `print_ticks()` 之后，确保第三条统计信息先输出，再发起关机请求。

| 累计 ticks | 本次统计输出 | 输出后的累计次数 | 是否调用关机接口 |
| --- | --- | --- | --- |
| 1～99 | 无 | 0 | 否 |
| 100 | `100 ticks` | 1 | 否 |
| 200 | `100 ticks` | 2 | 否 |
| 300 | `100 ticks` | 3 | 是，位于第三次输出之后 |

该策略不会在 100 或 200 次中断时提前请求关机。`sbi.c` 通过 `SBI_SHUTDOWN` 对应的 SBI 调用发出请求；当前验证能够证明调用时点和先后顺序，固件是否实际完成关机仍需完整内核运行确认。

已有 `print_ticks()` 在定义 `DEBUG_GRADE` 时会输出结束信息并执行 `panic()`。上述持续运行至 300 的正常路径以未启用该宏为前提；当前 `grade.sh` 使用的是 `GRADE_LAB3_*` 宏。这一已有行为保持原样。

#### 4.2.6 Specification 与实现约束

**前置条件。** `tf` 指向布局有效的 Trap frame；`tf->cause` 保存待处理原因。真实入口应已完成现场保存；时钟路径要求 `clock_init()` 已初始化 `ticks` 并提供可用的时钟和 SBI 接口。关机次数推导采用 `ticks` 从零开始、只由时钟处理路径按次递增的约定。

**后置条件。** 在关机接口调用前，S 模式时钟事件每处理一次，安排一次下一事件并使 `ticks` 增加一次；每 100 次调用一次 `print_ticks()`。统计输出次数达到 3 时，在本次输出之后调用 `sbi_shutdown()`。函数不写入传入 Trap frame，非关机路径通过既有返回接口交还控制流。

| 分类情况 | 规定的行为与可检查条件 |
| --- | --- |
| Case 1：`IRQ_S_TIMER` | 先设置下一事件，再计数；持续处理至至少 200 次，100 和 200 处均有统计输出 |
| Case 2：`IRQ_S_SOFT` | 输出 `Supervisor software interrupt`，不增加时钟计数 |
| Case 3：其他已知中断 | 按项目 `IRQ_*` 常量输出对应提示，保留现有接口 |
| Case 4：未知中断 | 输出移除中断标志后的原因码，例如 `Unknown interrupt: cause 15`，随后调用 `print_trapframe(tf)` |
| Case 5：关机条件 | 本次明确采用 `SHUTDOWN_AFTER=3`；在 300 ticks 的第三次统计输出后调用关机接口 |

约束包括：正确处理最高位与原因码；不修改 `tf->epc`、通用寄存器或保存的状态；保留 lab3 标记；不修改 `trap_dispatch()`、`trapentry.S`、`clock.c`、`init.c`、异常处理区域或评分脚本。中断函数本身没有补齐其他模块，也没有通过更改测试来绕过依赖缺口。

## 六、实验总结与收获

### 6.1 Trap 机制与操作系统原理的联系

**同步异常与异步中断具有共同入口，也有不同的返回语义。** 当前分发函数通过 `scause` 的最高位区分两类事件。异步时钟用于响应外部时间推进，中断函数保护原返回位置；断点和非法指令与当前执行的指令相关，需要异常处理程序明确后续执行策略。是否修改 EPC，应由事件语义和指令长度决定。

**Trap frame 是汇编与 C 之间的状态约定。** `SAVE_ALL` 的槽位顺序必须与 C 结构一致，C 函数才会读到正确原因与状态；返回路径还必须把保存内容准确写回。函数级测试证明没有修改一块现场内存，只覆盖其中一环；CPU 的寄存器和栈能否恢复，需要实际跨越入口与 `sret` 的往返验证。

**特权级与中断使能需要分层理解。** 当前目标是 S 模式内核，中断向量与全局使能由内核配置，具体时钟来源通过 `sie` 选择，计时和关机则通过 SBI 请求固件服务。中断处理函数没有承担设置全部特权级路由、驱动所有中断控制器或完成跨用户态栈切换的职责。

**周期性服务由多次后续事件设置形成。** `clock_init()` 建立首个事件，而每次 `IRQ_S_TIMER` 处理都重新设置下一事件，才能支持持续累计。`ticks` 进一步把离散事件转换为统计周期，但它还不是调度器：当前代码没有进程切换、时间片分配或阻塞唤醒。

**统计策略与机制可以保持清晰边界。** 每次时钟计数和重设是定时服务的基础机制；每 100 次打印以及第三次打印后关机，是本次采用的观测与终止策略。`SHUTDOWN_AFTER=3` 使选择显式可见，通过已有 `ticks` 推导输出次数，也避免了另一个计数状态与 `ticks` 不一致。
